# Offline benchmark: qwen3.5:9b (2026-11-02)

A free, local run of the full `finance_v1` benchmark through Ollama. It measures how AskData performs with a small open model on a laptop. **It is not a Claude result.** The Claude rows in the README stay "pending" until a keyed run.

## Setup

| | |
|---|---|
| Model | `qwen3.5:9b`, Q4_K_M (6.6 GB), served by Ollama 0.40.13 |
| Hardware | RTX 4050 Laptop (6 GB VRAM), Ryzen 7 8845HS, 16 GB RAM. About 55% of the model ran on the GPU. |
| Settings | temperature 0, no thinking, 6144-token context, one question at a time |
| Code | git `46716fe`, prompt `generate_sql@v1` |
| Dataset | `finance_v1`: all 91 cases (79 SQL, 6 clarify, 6 unanswerable). One repeat, because at temperature 0 extra repeats add little. |
| Duration | 4 h 40 min for all 7 configs (~40 min each, ~20 s median per question). No outages, crashes or resumes. |

The raw per-config summaries are in [`2026-11-02-qwen3.5-9b.json`](2026-11-02-qwen3.5-9b.json).

## Ablation

Each row adds one capability to the row above it. `full` is the production config: no few-shot, and linking only above 40 columns (see [evaluation.md](../evaluation.md)).

| Config | Overall accuracy (95% CI) | SQL execution acc. | Clarify / unanswerable | First attempt | Exec-error rate | Median latency |
|---|---|---|---|---|---|---|
| schema_only | 40.7% (31.9–51.6) | 36.7% | 66.7% | 36.7% | 7.6% | 20.8 s |
| +samples | 47.2% (37.4–57.1) | 44.3% | 66.7% | 44.3% | 8.9% | 21.7 s |
| +linking | 48.4% (39.6–58.2) | 45.6% | 66.7% | 45.6% | 8.9% | 20.8 s |
| +glossary | 50.5% (40.7–60.4) | 45.6% | 83.3% | 45.6% | 17.7% | 21.7 s |

**By tag:** single-table 79.4%, filter 66.7%, aggregation 48.4%, subquery 44.4%, date logic 30.0%, join 20.4%, glossary 7.7%, window 0% (4 cases).

## What it shows

- **The pipeline helps even a small model.** Going from schema-only to production fixes 12 questions and breaks 3 (+9 net). That's significant on a sign test (p ≈ 0.035).
  - Sample values are the biggest single step (+6 net). They teach the model real category names and status values.
- **Most single steps are within noise.** With 91 questions the confidence intervals are about ±10 points wide, so the 1–3 point differences between adjacent configs don't establish an order. Treat the ablation as directional.
- **The glossary helps kind decisions but trips the model on columns.** Clarify/unanswerable accuracy rises from 66.7% to 83.3%. But failing queries double (7 → 14), and 12 of the 14 are glossary questions. In 7 of them the model reads the category group from the wrong table (e.g. `merchants.category_group`) while applying the *spend* definition; the config before it had none of these.
- **Self-correction barely works at this size.** In production, 17 questions needed a retry and only 1 was recovered. The model usually repeats the same mistake even when given the error message.
- **Few-shot examples hurt slightly** (−3 net, within noise), which supports leaving them out of production.
- **Joins and glossary terms are the weak spot.** Most failures are multi-table questions (20% on joins) and the precise finance definitions (8% on glossary). The 9B model handles single-table questions well (79%) but loses track of join keys and filters across three tables.

## Caveats

- The demo data and benchmark are synthetic (see [evaluation.md](../evaluation.md#known-limitations)).
- Latency is laptop-specific. The median is dominated by local token generation with part of the model in system RAM, not by AskData itself.
- This was one repeat at temperature 0, so the CIs reflect question sampling, not run-to-run variation.
