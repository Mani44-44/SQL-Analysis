# Evaluation methodology

AskData measures itself against a benchmark that lives in this repository and runs offline. This document covers what is measured, how it is scored, and what the numbers do and don't mean.

## Dataset: `finance_v1`

| | |
|---|---|
| Source | `eval_data/build_finance_v1.py`, which writes `eval_data/finance_v1.jsonl`. A test keeps the two in sync. |
| Data | The seeded synthetic personal-finance workspace from `app/demo/generate.py` (seed 42): about 1.1k transactions from Jan 2025 to Jun 2026, plus accounts, merchants, categories and budgets. |
| Size | 91 cases: 79 answerable (SQL), 6 ambiguous (expected `clarify`), 6 unanswerable |
| Difficulty | easy 29 · medium 48 · hard 14 |
| Tags | single_table, aggregation, filter, join, date_logic, subquery, window, glossary, ambiguous, unanswerable |
| Smoke subset | 28 cases flagged `smoke`, covering every tag and every expected kind |

**Authoring rules**
- Questions are phrased so that one reading is correct, given the workspace glossary. The exceptions are the `ambiguous` and `unanswerable` cases.
- Gold SQL returns only the columns the question asks for, so a prediction with extra columns can still earn a superset match.
- "Spend" follows the glossary: successful debits, excluding the Transfers and Savings category groups, with ATM withdrawals that have no merchant included.
- No case may return an empty result. An empty gold result would let a wrong prediction that also returns nothing count as a match.

**Gold verification.** `python -m app.eval.run --check-gold` runs in CI. For every gold query it checks three things:
1. The query passes the SQL guard and executes.
2. It returns at least one row.
3. It produces identical values and types when run raw and when regenerated by sqlglot. This guards decision D-012, which executes the regenerated SQL.

Every gold query was also inspected by hand against the data during authoring. One case (fin-079) was rewritten because its result was empty.

**Leakage guard.** `tests/eval/test_harness.py::test_no_benchmark_leakage` checks that no benchmark question appears in the prompts. It also checks that no few-shot or demo-suggestion question has a token Jaccard similarity of 0.8 or more with any benchmark question.

## Scoring

**Execution match.** This is implemented in `app/eval/matching.py`. Gold and predicted results are compared as follows:
- **Columns:** column order and column names are ignored. Each predicted column is mapped onto a gold column with an equal value multiset, and the row-level pairing must also hold.
- **Rows:** compared as a multiset, unless the gold SQL has a top-level `ORDER BY`, in which case row order must match.
- **Numbers:** values with |x| ≥ 1 are rounded to 2 decimal places. Values with |x| < 1 are compared to 4 significant digits. Integers equal floats of the same value.
- **NULL and booleans:** NULL equals NULL. A boolean never equals 0 or 1.
- **Dates:** `2025-01-01T00:00:00` equals `2025-01-01`, and a `YYYY-MM` label equals the first day of that month.
- **Strict vs superset:** a *strict* match needs the same number of columns. A *superset* match allows extra predicted columns. Both need the same number of rows.

**Per-case correctness.** A SQL case is correct when its result is a strict execution match. An ambiguous or unanswerable case is correct when the predicted `kind` matches the expected one.

**Metrics.** These are reported by `app/eval/metrics.py`.
- **Overall accuracy,** with a 95% percentile-bootstrap confidence interval (1,000 resamples, using cases as the resampling unit).
- **Execution accuracy** and **superset accuracy** on the SQL cases.
- **First-attempt accuracy:** whether the first SQL the model produced matched, before any self-correction.
- **Self-correction recovery rate:** of the cases that were wrong on the first attempt, the share that were right in the end.
- **Kind accuracy:** on the ambiguous and unanswerable cases.
- **Valid-SQL rate** and **execution-error rate.**
- **Latency** (p50 and p95), **cost per case,** and token totals.
- **Breakdowns** by difficulty, by tag, and by failure category.

**Failure categories.** Each wrong case gets one category, assigned by heuristics over the sqlglot ASTs. The first rule that matches wins, in this order: `kind_mismatch`, `hallucinated_column`, `validation_error`, `execution_error`, `wrong_table`, `wrong_join`, `wrong_aggregation`, `date_handling`, `wrong_filter`, `wrong_columns`, `other`.

## Noise and the regression gate

- Use several repeats (`--repeats 3`). The report shows accuracy for each repeat alongside the bootstrap confidence interval.
- In CI (`.github/workflows/eval.yml`), PRs run the smoke subset twice. The run fails if accuracy drops more than 5 points below `eval_data/baseline.json`. That threshold sits above the run-to-run noise observed on the smoke set.
- The gate is skipped until a baseline is set with a real key: `--update-baseline`.

## The oracle run is not model accuracy

`--provider oracle` runs the whole harness with a deterministic stand-in that answers from the gold labels and fails on purpose in a fixed pattern. The expected metrics are known exactly and checked in `test_oracle_benchmark_exact_metrics`. These numbers validate the harness and must never be reported as accuracy.

## Known limitations

- The data is synthetic. Real bank exports are messier and more varied, so accuracy here may overstate accuracy on real uploads.
- Each case has a single gold query. Some questions have more than one defensible reading even with the glossary, and those cases can understate accuracy.
- Ambiguity labels are a judgement call. A model that answers with a sensible default plus a stated assumption is scored as wrong on `clarify` cases.
- A public benchmark subset (Spider or BIRD) is planned but not included yet. It needs a download and has license terms. See `docs/PLAN.md` P10.
